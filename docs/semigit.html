SemiGit

AI-Powered Semantic Commit Generation — VS Code Extension

TypeScript · Strict 90+ Tests Passing One Universal .vsix Fully Offline MIT License
Commits should mark what changed, not when you got tired.

Overview

SemiGit is a local-first VS Code extension that watches your coding session, understands each change structurally (via the TypeScript compiler) and semantically, detects when you've crossed a feature-level milestone, and generates a Conventional Commit for it.

It runs fully offline by default (no API key, no network), ships as one universal build (SQLite compiled to WebAssembly — no native module, no per-OS packaging), and its output quality is measured against real git history rather than asserted.

StackTypeScript (strict) · VS Code Extension API · TS Compiler API · React + Tailwind (webview) · sql.js (SQLite → WASM) · Drizzle · Zod · simple-git · Turbo monorepo

Why SemiGit

Most git history is noisy: wip, fix, stuff, final2. That happens because commits are made when a developer feels done — an arbitrary point in time — and writing a good message is friction, so people don't.

Existing tools format a message you already typed. None of them decide when a commit should happen or what it represents, based on the actual code change. SemiGit does both:

  1. It watches saves and diffs your code's structure (functions, classes, methods, interfaces, components, imports) — not line counts.
  2. It scores whether you've reached a feature-level milestone.
  3. When you have, it writes the Conventional Commit for that unit of work.

Features

  • Semantic milestone detection — a weighted score over structural change volume, files touched, session duration, and analysis confidence.
  • Conventional Commit generation — type(scope): subject plus a body summarizing what changed.
  • Three commit modes — Suggest (default), Automatic, Hybrid.
  • Works fully offline — a deterministic heuristic engine means zero setup, zero cost, zero network.
  • Optional AI providers — OpenAI, Anthropic, Google Gemini, DeepSeek, and local Ollama, behind one interface with automatic fallback to the offline engine.
  • Compiler-grade parsing — JS/TS structure comes from the TypeScript Compiler API.
  • Live sidebar — current session, milestone score, detected feature, commit suggestions.
  • Dashboard — commit frequency, session time, and a development timeline.
  • Per-commit provider attribution — analytics distinguish AI-generated from heuristic commits.
  • Evaluation harness — replay the pipeline over real git history and measure output quality.
  • One universal .vsix — no native module, no ABI matching, no system Node requirement.

Usage Guide

The basic loop

  1. Open a git repo with supported source files and make sure the SemiGit sidebar is visible.
  2. Write code and save (Ctrl/Cmd+S). SemiGit only analyzes on save, not on every keystroke.
  3. After the debounce window (default 2s), the sidebar updates: Current session (elapsed time, files changed, milestone-score progress bar), Detected feature (inferred name + confidence), and Suggestions (a commit card once the score crosses the threshold).
  4. Click Commit on the suggestion card. SemiGit stages those files and creates the commit.

Forcing an evaluation

  • SemiGit: Evaluate Milestone Now — score the session immediately and report the result.
  • SemiGit: Generate Commit — build a commit draft right now, regardless of the threshold.

Commit modes

Set semigit.commitMode:

ModeBehavior
suggest (default)Shows a suggestion card. Nothing is committed until you click.
automaticCommits as soon as a milestone is detected (score ≥ suggestThreshold). No prompt.
hybridSuggests normally, but auto-commits when the score is high (≥ autoCommitThreshold).
Noteautomatic and hybrid create commits with no confirmation. They never push unless you explicitly enable semigit.autoPushToRemote. To undo an unwanted commit, use git reset --soft HEAD~1 (your changes stay staged).

The dashboard

SemiGit: Open Dashboard shows:

  • Metric tiles — total commits, AI-generated commits, average commit size, features completed, refactors, sessions
  • Commit frequency — a bar chart over time
  • Session time — minutes coded per day
  • Timeline — an append-only feed of sessions, milestones, generated commits, and created commits

Why some settings are machine-scoped

commitMode, autoCommitThreshold, autoPushToRemote, and servicePath are machine-scoped deliberately. A repository you clone ships its own .vscode/settings.json; if these were workspace-scoped, an untrusted repo could silently switch you into automatic mode, enable pushing, or point the extension at an arbitrary executable. Machine scope means only your User settings can change them.

Tuning the milestone threshold

  • Commits triggering too often → raise suggestThreshold (e.g. 0.65).
  • Commits never triggering → lower it (e.g. 0.35), or use Evaluate Milestone Now to see the current score and the reasons behind it.

AI Providers

AI is entirely optional. The default heuristic provider is deterministic, offline, and free. An LLM only improves the quality of the feature label and commit subject — it is never required to detect milestones or create commits.

Setting one up

  1. Ctrl/Cmd+Shift+P → SemiGit: Choose AI Provider
  2. Pick Offline (heuristic), Local LLM (Ollama), or Cloud API → provider
  3. Paste your key when prompted
  4. Run SemiGit: Test AI Provider → expect ✓ "<provider>" responded

What actually gets sent

Cloud providers receive only a sanitized structural summary: repository name, file paths, changed identifier names, and a semantic summary — never your raw file contents. All free-text fields pass through a prompt-injection sanitizer before interpolation, and responses are normalized through a strict Zod schema.

Key storage

Keys are stored in the OS keychain via VS Code SecretStorage, passed to the local service in memory only, and never written to disk, the database, or logs. Any provider failure (bad key, network error, rate limit) silently falls back to the offline heuristic.

Cost

One LLM call happens per milestone evaluation — not per keystroke or save. With the cheap default models this is negligible.

How It Works

The pipeline

save file → capture (extension)
          → AST diff (TS compiler)
          → semantic categorization
          → feature analysis (AI or heuristic)
          → milestone score ≥ threshold?
              ├─ no  → keep watching
              └─ yes → commit draft (Conventional Commit)
                        ├─ Suggest   → show in sidebar
                        ├─ Automatic → commit now
                        └─ Hybrid    → commit if score high
  1. Capture — the extension watches saves/creates/deletes for enabled languages and sends the path, event type, and content to the local service.
  2. AST diff — the file's previous and current content are parsed and compared, producing structural deltas: function login added, method refresh removed, etc.
  3. Semantic categorization — deltas are aggregated into a human-readable summary and a Conventional Commit category (feat, fix, refactor, docs, test, chore, …), with file-path heuristics for tests/docs/config.
  4. Feature analysis — the active provider (AI or heuristic) produces a normalized FeatureAnalysis: label, category, confidence, suggested type, scope, rationale.
  5. Milestone scoring — see the formula below.
  6. Commit generation — a Conventional Commit header plus a body listing the rationale and files.
  7. Persistence — every stage is recorded; the timeline and analytics update live.

The milestone score

A weighted sum of five saturating signals, all normalized to [0, 1]:

score = 0.15 × files
      + 0.25 × structural
      + 0.15 × duration
      + 0.25 × featureConfidence
      + 0.20 × aiConfidence
SignalSaturates at
files changed5 files
structural changes8 entity deltas
session duration30 minutes

A commit is suggested when score ≥ suggestThreshold (default 0.5), and auto-created in hybrid mode when score ≥ autoCommitThreshold (default 0.8). Every decision carries a human-readable reasons list explaining the score.

Architecture

Three processes, three trust boundaries

┌─ VS Code Extension Host ──────────────────────────┐
│ extension: service supervisor · commands · status │
└──────┬──────────────────────────────┬─────────────┘
       │ JSON-RPC over stdio          │ postMessage (Zod-validated)
┌──────▼──────────────────────┐  ┌────▼──────────────────────┐
│ Local Service (Node child)  │  │ Sandboxed Webview (CSP)   │
│ · JSON-RPC handlers (Zod)   │  │ · React sidebar+dashboard │
│ · pipeline + engines        │  └───────────────────────────┘
│ · sql.js — SQLite in WASM   │
│ · simple-git (no shell) → git
└─────────────────────────────┘

Why three processes?

  • The webview is a sandboxed browser context — it can't touch the filesystem, so UI code is isolated from your machine.
  • The extension host is shared with every other extension; keeping analysis out of it means a heavy parse never freezes your editor.
  • The service is a child process the extension supervises, restarts on crash, and can kill.

Nothing crosses a boundary without passing a Zod schema at runtime. A compile-time drift check ensures the schemas can never silently diverge from their TypeScript types.

Design principles

  • Interface seams everywhere — LanguageParser, AIProvider, and the repository layer are all swappable without touching orchestration. Swapping SQLite→WASM and regex→TS-compiler each touched one implementation file.
  • Deterministic core — every engine is pure and synchronous; AI is an optional enhancement, not a dependency.
  • Composition root — all wiring happens in one container; no service locators or globals.

What is not stored

  • Your source code. File contents are used in memory to compute the AST diff, then discarded. Only derived facts ("a function named login was added") persist.
  • Your API keys. They live in the OS keychain and in service memory only.

Network

Zero network traffic with the default heuristic provider. With a cloud provider, exactly one request per milestone evaluation, carrying only the sanitized structural summary. There is no telemetry, no analytics upload, and no account.

The Backtest / Evaluation Harness

How do you know the milestone detection and message generation are actually good? Measure them.

npm run backtest -- <path-to-git-repo> [--limit N] [--json]

The harness replays the exact same engines the live extension uses over a repository's real commit history — reconstructing each commit's before/after for every changed file — and compares what SemiGit would have generated to what the developer actually wrote.

MetricMeaning
Milestone-boundary flag rate% of real commits SemiGit would have recognized as a commit point. A calibration proxy — humans commit at real boundaries.
Commit-type match rate% of real Conventional Commits whose type SemiGit matched. Shown as n/a for repos that don't use Conventional Commits.
Avg subject word-overlapRough text similarity to the human subject. Human messages are terse and varied, so low values are expected; treat this as directional only.

It also prints per-commit real → generated rows so you can eyeball the quality. This is the feedback loop used to tune the scoring weights and message heuristics: change the code, re-run the backtest, and watch the numbers move.

Troubleshooting

The service won't start / the sidebar says "Not connected"

  1. Open View → Output and select SemiGit from the dropdown — all service logs and errors go there.
  2. Make sure npm run build completed (the build copies the service and UI into the extension).
  3. Try SemiGit: Restart Service.
  4. If the service crashes repeatedly, the extension stops it and shows a notification with a Restart Service action.

No suggestions ever appear

CheckFix
Is the folder a git repo?Run git init
Did you save the file?Analysis runs on save, not on typing
Is the file a supported type?.ts .tsx .js .jsx .py
Is the language enabled?Check semigit.enabledLanguages
Is the score below threshold?Run Evaluate Milestone Now to see the score and reasons; lower semigit.suggestThreshold
Change too small?The score needs meaningful structural change — one-line edits won't trigger it

The commit fails

  • Ensure git is installed and on PATH.
  • Ensure the folder is a git repository with changes to stage.
  • "No staged changes to commit" means the files in the draft had nothing to stage.
  • If you exceed semigit.maxFilesPerCommit, the commit is refused by design — raise the cap or commit manually.

AI isn't being used (it silently fell back to the heuristic)

Run SemiGit: Test AI Provider. It reports the exact reason:

MessageCause
provider is set to "heuristic" (offline)You haven't selected an AI provider
No API key set for this providerRun Set API Key
An HTTP/auth errorBad or expired key
A network/timeout errorConnectivity, or Ollama isn't running

Any failure is non-fatal — SemiGit continues with the offline engine.

The sidebar or dashboard is blank

The webview has an error boundary; it will display the error and a reload action. Check the SemiGit output channel for a clientError line, then reload the window (Developer: Reload Window).

Analytics look wrong with multiple VS Code windows open

Each window runs its own service instance against the same database file. Concurrent writes are last-writer-wins, so some recent analytics rows can be lost. Writes are atomic, so the file never corrupts — and your git history is never affected. Prefer one window at a time for accurate analytics.

Resetting everything

Delete the database file (see Data & Privacy) and restart. This clears sessions, timeline, and analytics. It does not touch your git history.

FAQ

Does it commit automatically without asking?
Not by default. semigit.commitMode is suggest, which only shows a card — nothing is committed until you click. automatic and hybrid do commit unattended if you enable them.

Does it push to my remote?
No. semigit.autoPushToRemote defaults to false, and it's machine-scoped so a cloned repo can't turn it on.

Do I need an API key?
No. The offline heuristic is the default and handles the entire pipeline, including auto-commit.

Is my source code sent to an AI provider?
No. Only a sanitized structural summary — file paths, changed identifier names, and a semantic summary. Raw file contents never leave your machine.

Do I need Node.js installed to use the extension?
No. The service runs on VS Code's own runtime. Node is only needed to build from source.

Which languages are supported?
TypeScript, TSX, JavaScript, JSX (via the TypeScript compiler) and Python (heuristic parser).

Can I undo an automatic commit?
Yes — git reset --soft HEAD~1 keeps your changes staged.

Does it work offline?
Completely, in the default configuration.

Security

SemiGit crosses several trust boundaries, so these invariants are enforced and documented:

  • Prompt-injection sanitization — repo names, paths, and identifiers are attacker-influenced, so all free text is sanitized (newlines, backticks, tags, override tokens stripped; length capped) before entering a prompt.
  • Untrusted webview — every postMessage payload is validated with a schema before being forwarded; the webview runs under a strict nonce-based CSP with no unsafe-inline/unsafe-eval.
  • Validated RPC boundary — every parameter is schema-checked: paths must be absolute, contain no null bytes, and no .. traversal after normalization.
  • Secrets never persisted — API keys live in the OS keychain and service memory only, and the logger redacts sensitive fields. Logs go to stderr, never stdout (which carries the RPC stream).
  • Git without a shell — all git access goes through simple-git with arguments passed as an array and a -- separator, so a filename can never be interpreted as a flag. No child_process.exec, no shell: true.
  • Commit caps — every commit path enforces maxFilesPerCommit.
  • Machine-scoped destructive settings — an untrusted workspace cannot enable auto-commit, auto-push, or redirect the service executable.
  • Bounded memory — all caches keyed by session or repository have eviction limits.

Limitations & Roadmap

Known limitations

  • Python analysis uses the heuristic parser, not a full grammar — less precise than JS/TS.
  • Milestone weights are hand-tuned, not learned.
  • Concurrent VS Code windows share one database; recent analytics writes are last-writer-wins.
  • Generated subjects describe structure ("add AuthService"); only an LLM can infer deeper intent.

Possible next steps

  • Tree-sitter grammars bundled by default for Python parity
  • Learned or user-tunable milestone weights informed by the backtest
  • Inline commit preview and editing before committing
  • Heuristic-vs-AI comparison run through the evaluation harness
